## Часть 3. Три запроса, которые база отклоняет

Таблица `reviews` создана с именованными ограничениями: `reviews_rating_range` (оценка от 1 до 5),
`reviews_one_per_user_event` (один студент — один отзыв на мероприятие), `reviews_event_fk` и
`reviews_user_fk` (внешние ключи с каскадным удалением).

### 1. Оценка 6

```sql
INSERT INTO reviews (event_id, user_id, rating) VALUES (1, 6, 6);
```

```
ERROR:  new row for relation "reviews" violates check constraint "reviews_rating_range"
DETAIL:  Failing row contains (3, 1, 6, 6, null, 2026-11-05 19:43:33.108261+07).
```

### 2. Второй отзыв того же студента на то же мероприятие

Анна (4) уже оставила отзыв на лекцию (1).

```sql
INSERT INTO reviews (event_id, user_id, rating) VALUES (1, 4, 3);
```

```
ERROR:  duplicate key value violates unique constraint "reviews_one_per_user_event"
DETAIL:  Key (event_id, user_id)=(1, 4) already exists.
```

### 3. Отзыв на несуществующее мероприятие

```sql
INSERT INTO reviews (event_id, user_id, rating) VALUES (999, 6, 5);
```

```
ERROR:  insert or update on table "reviews" violates foreign key constraint "reviews_event_fk"
DETAIL:  Key (event_id)=(999) is not present in table "events".
```

Имена ограничений видны прямо в тексте ошибки, поэтому по сообщению сразу ясно, какое правило нарушено.
Без явных имён PostgreSQL подставил бы автоматические (`reviews_rating_check`, `reviews_event_id_user_id_key`,
`reviews_event_id_fkey`), и их пришлось бы расшифровывать.

## Часть 3. Можно ли выразить правило ограничением в таблице `reviews`?

Правило: «оставить отзыв может только тот, кто был записан на мероприятие, и только после его окончания».

**Нет, ограничением таблицы `reviews` это не выразить.** У правила два условия, и оба выходят за возможности ограничений:

1. **«Был записан»** требует посмотреть в другую таблицу, `registrations`. `CHECK` видит только ту строку,
   которую вставляют, и не может делать подзапросы к другим таблицам. Внешний ключ из `reviews`
   на `registrations (event_id, user_id)` тоже не подходит: ключ может ссылаться только на уникальный
   набор столбцов, а в `registrations` уникальность задана частичным индексом (`WHERE status = 'active'`),
   то есть не на всю таблицу. К тому же ключ проверяет только наличие записи, но не её статус и не то,
   что запись не отменена.
2. **«После его окончания»** сравнивает время окончания мероприятия (`events.ends_at`, другая таблица)
   с текущим моментом. Во-первых, снова нужна другая таблица. Во-вторых, `now()` меняется со временем,
   а ограничение проверяется только при вставке и изменении строки: оно не может «созреть» позже.

**Где тогда проверять.** В сервисном слое API, в той же транзакции, что и вставка отзыва: сначала
запросом убедиться, что у пользователя есть активная запись на это мероприятие и что `ends_at < now()`,
и только потом выполнять `INSERT`. Нарушение отдавать как понятную ошибку (409 или 422). Альтернатива,
если правило нужно удержать на уровне самой БД, — триггер `BEFORE INSERT` на `reviews`, который делает
те же проверки. Но триггер — это уже код, а не декларативное ограничение, и его труднее поддерживать,
поэтому для учебного проекта основным местом проверки выбираем сервисный слой. Ограничения в таблице
при этом остаются как последний рубеж для правил, которые видны в самой строке: диапазон оценки,
один отзыв на пару «студент — мероприятие», существование мероприятия и пользователя.

## Часть 4. Гонка за BR-3: один студент записывается дважды

Запись добавляется командой `INSERT INTO registrations (event_id, user_id) VALUES (2, <id>);`.
В таблице `registrations` есть частичный уникальный индекс `registrations_one_active (event_id, user_id)
WHERE status = 'active'`: у одного студента не может быть двух активных записей на одно мероприятие.

### Сценарий 1: Вера (user_id = 6), окно A завершает `COMMIT`

| Шаг | Окно | Действие | Что наблюдал |
|---|---|---|---|
| 1 | A | `BEGIN;` `INSERT ... VALUES (2, 6);` | `INSERT 0 1`, строка пока не закоммичена |
| 2 | B | `BEGIN;` `INSERT ... VALUES (2, 6);` | Команда не возвращается: курсор «зависает», приглашение `webois=*#` не появляется |
| 3 | A | `COMMIT;` | `COMMIT` |
| 4 | B | (ждёт результата) | Сразу после `COMMIT` в A приходит `ERROR: duplicate key value violates unique constraint "registrations_one_active"`, `DETAIL: Key (event_id, user_id)=(2, 6) already exists.` |
| 5 | B | `COMMIT;` | Транзакция уже прервана ошибкой, поэтому `COMMIT` превращается в `ROLLBACK`. Итог: в таблице одна запись Веры, из окна A |

### Сценарий 2: Дима (user_id = 7), окно A завершает `ROLLBACK`

| Шаг | Окно | Действие | Что наблюдал |
|---|---|---|---|
| 1 | A | `BEGIN;` `INSERT ... VALUES (2, 7);` | `INSERT 0 1`, строка не закоммичена |
| 2 | B | `BEGIN;` `INSERT ... VALUES (2, 7);` | Окно зависает, как и в первом сценарии |
| 3 | A | `ROLLBACK;` | `ROLLBACK` |
| 4 | B | (ждёт результата) | Сразу после отката `INSERT` в B проходит: `INSERT 0 1`, ошибки нет |
| 5 | B | `COMMIT;` | `COMMIT`. Итог: в таблице одна запись Димы, из окна B |

Чтобы увидеть, что окно B именно ждёт, в третьем окне можно выполнить:

```sql
SELECT pid, wait_event_type, wait_event, state, query
FROM pg_stat_activity
WHERE datname = 'webois' AND wait_event_type = 'Lock';
```

Окно B показывает `wait_event_type = Lock`, `wait_event = transactionid`: оно ждёт завершения транзакции A.

### Объяснение

Окно B не может сразу ни вставить строку, ни получить ошибку, потому что исход зависит от чужой транзакции: строка из окна A ещё не закоммичена, и пока A не завершилась, база не знает, останется она или исчезнет. После `COMMIT` в A запись Веры становится настоящей, и вставка B нарушает уникальный индекс `registrations_one_active`; после `ROLLBACK` строки нет, и вставка B проходит, поэтому сценарии заканчиваются по-разному. `FOR UPDATE` здесь не понадобился, потому что обе транзакции пишут строку с одним и тем же ключом `(event_id, user_id)`, и сам уникальный индекс ставит их в очередь. В гонке за последнее место студенты разные, строки у них с разными ключами, и индекс их не сталкивает: обе транзакции прочитают «места есть» и обе вставят строку. Поэтому там нужно вручную сериализовать их блокировкой строки мероприятия через `SELECT ... FROM events WHERE id = ... FOR UPDATE`.
